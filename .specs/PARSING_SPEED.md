# 解析速度优化

修改基于 Git 检查点 `0ebaa3f`。

## 行为与实现

- YouTube 的 PO Token 辅助服务改为由 Electron 按需启动并持有，多个解析/下载任务共享一次启动。并发首次请求合并；单个任务取消或结束不会关闭其他任务正在使用的服务。应用关闭、控制管道断开或服务进程退出时释放资源，下次请求可重新启动。
- Python 任务只借用经过版本核对的 `http://127.0.0.1:<port>` 服务。没有共享服务参数的旧调用继续使用原来的任务生命周期；共享服务启动失败时不在同一任务内重复等待一轮启动。
- 代理解析与服务准备并行。YouTube 下载前、执行前的服务端登录检查和 Python 的登录凭据检查保持不变。
- 抖音优先使用匹配视频 ID 的缓存/当前页面数据。缺失时给页面约 400ms 优先时间，再并行补取详情；先取得有效数据的一方胜出，取消另一方。页面读取与补取分别有 7 秒、10 秒的等待窗口，不再串行累加。补取结果缓存 5 分钟；不刷新左侧页面。
- Vimeo 对 HLS/DASH 的各 CDN 分支最多使用 4 个并发请求流程，分别使用独立下载器、Cookie 容器和请求处理器。按原顺序合并全部格式和字幕，不删线路；分支异常时通过原解析器重试该分支。单线路、直播及不熟悉的配置结构交回原流程。
- Vimeo 的解析与下载注册相同适配器，保留原格式编号及同 CDN 音轨匹配。签名流地址继续只存在于本机工作进程中，不进入右侧公开状态。
- 自动解析默认关闭、手动模式保留上次结果、分组及组内标签行为均不变。后台补取只在实际解析任务中发起。

## 验证

- 52 项 JavaScript 逻辑检查通过，其中新增 14 项覆盖服务复用、独立取消、失败重启、启动超时、退出清理、抖音两路竞争、错视频拒绝和读取截止时间。
- 149 项 Python 回归断言通过，其中新增 9 项覆盖共享服务端点与生命周期、旧调用兼容、控制管道 EOF、Vimeo 并发/顺序/音轨/Cookie 隔离及分支失败回退。最后一次 Vimeo 兼容性调整后，相关 40 项重新通过。
- 合并运行整套 Python 检查时出现两条 bgutil 插件重复注册诊断；149 项断言通过。独立工作进程及相关 40 项检查未出现这两条诊断，未修改第三方依赖包。
- 97 项 Electron 受控界面检查及第二进程恢复检查通过，包括各站预览、下载目标绑定、取消、结果保留、自动模式跟随和登录限制。
- 实际启动共享服务约 1161ms，再次取用不足 1ms；一个借用者结束后服务仍可响应。实际调用应用关闭流程后，服务端口关闭且后台任务集合清空。

## 公开样例与耗时范围

使用独立配置，不导入现有账号，不实际下载媒体。耗时从发起解析开始，不包含打开网页的等待；只是该网络环境下的小样本。

| 场景 | 本轮记录 |
| --- | --- |
| Vimeo `754255543`，交替运行原解析器/并行解析器 | 原流程 3776 / 4439ms，并行流程 2036 / 1620ms；4 次返回的 22 个格式编号、分辨率和音视频编码元数据一致 |
| 抖音 `7692375985957752098`，模拟当前页面快照缺失，真实后台浏览器补取 | 2837ms，18 个格式、封面可用；仅补取 1 次，左侧导航/刷新次数为 0 |
| 同一抖音再次解析 | 282ms，复用缓存，没有再次补取 |
| YouTube `jNQXAC9IVRw`，通过应用真实任务桥连续请求固定地址 | 服务首次启动 1175ms；之后两次任务为 5313 / 3393ms，同一服务进程，均返回 24 个格式 |

完整 Electron 测速中，Vimeo 还出现过一次 9294ms 的慢请求，因此不能把上述改善视为固定时延保证。YouTube 初始完整流程有一次未取得结果；后续连续浏览器验证记录到页面导航取消，另一次新会话页面加载超时。固定地址任务桥检查排除了浏览器自动跳转，验证了真实解析与应用退出清理；未以这些取消或超时记录计算提速比例。
